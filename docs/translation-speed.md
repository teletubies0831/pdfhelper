# 翻译卡片为什么慢，以及现在快在哪

用户反馈："翻译这段英文大约用了 7s，有些太慢了"。下面是把 7 秒拆开的结果，以及为它做的改动。
入口：`src/viewer/features/translation/`、`src/background/ai/translation-stream.ts`、`translation-prompts.ts`。

## 1. 7 秒花在哪

| 阶段 | 时间 | 原因 |
|---|---|---|
| 选区稳定防抖 | 0.7s | `AUTO_TRANSLATE_DELAY_MS`，防拖动时每动一下都发请求 |
| 提示词预填充 | 0.2–0.5s | 请求走 `pdf-helper:ai-chat`，于是背着**聊天助手的系统提示词**：Agent 工具规则、`memory.upsert` 规则、`[[PDF:P8|原文]]` 引用规范，约 2k token。翻译一句话要为这些付钱，而且它们还在鼓励模型"像文档助手那样回答"而不是"输出一个 JSON" |
| 生成 | **约 5–6s** | 一个 JSON 里塞了 `sourceTextLatex`（把英文原句整句重写一遍）+ `translation` + 最多 6 个重点词，每个词还带 `partOfSpeech`／`meaningInSentence`／**`reason`** |
| 渲染 | <50ms | **非流式**：闭合花括号到达之前，面板上什么都不动 |

`reason` 是提示词自己要求的——"先在 reason 里给出内部判定依据，并据此复核"——也就是让模型把思维链写进响应体，而解析后**直接丢弃**。6 个词 × 每段依据，大约是输出 token 的 30–50%，全部花在被扔掉的文字上。

## 2. 现在的形状：一次翻译，两路流

```
选区稳定 450ms
  ├─ 立刻渲染卡片骨架（原文来自本地，零网络）：原句翻译 / 重点单词
  ├─ 流 A（纯文本，约 512 token 上限）：只要译文 → 逐字出现
  └─ 流 B（JSON，约 768 token 上限）：只要 6 个重点词 → 译文出现后补进卡片
```

- **译文先到**。流 A 的提示词只有五条规则，输出就是中文译文本身，所以第一句话大约 1 秒内出现；面板上还有打字光标。
- **重点词后补**。流 B 与流 A 并行发出，落到卡片下方；它失败只会在原地写一行"重点词没有生成：…"，不碰上面的译文。
- **两条流互不等待**。任何一半失败都不会带走另一半。

## 3. 具体的三处省钱/省时

1. **提示词从"聊天助手"里摘出来**（`translation-prompts.ts`）：只保留译者/教师的角色和格式要求，不再带 Agent 工具、记忆、引用规则。约 2k token → 约 100 token。
2. **删掉 `reason` 与"先写依据再复核"**，保留筛选标准本身（用户要求重点词数量不变，仍是 6 个）：筛选质量来自"标准"，不来自"把标准复述一遍"。
3. **`sourceTextLatex` 只在句子真有公式时才要**（`sentenceNeedsLatex()`，看 `$ \` 数学符号与希腊字母）。原句正文本来就在客户端手里，让模型重写一遍既费 token 又容易改写错。

另外：`maxOutputTokens` 从 4096 降到 512 / 768（这是上限，不是目标，但能避免"预算越大越啰嗦"这一类行为），防抖 700 → 450ms。

## 4. 上线后第一轮反馈：卡片是空的

改完第一版后用户截图：「翻译内容直接空了」——面板上「2. 原句翻译」标题在，下面什么都没有，也没有任何提示。

原因是**两半的完成顺序**。重点词是"一次 JSON"，译文是"文本流"，谁先到不保证。第一版在**重点词那半**落地时就写历史记录，`translation` 取的是当时已累积的文本——如果重点词先到，就存下了一条 `translation: ''` 的记录。而下次选中同一句话时，历史缓存**短路了请求**（"已从当前 PDF 的历史记录中恢复结果"），于是渲染出一张空译文卡片，且永远不会自己好。

三处修好，缺一不可：

1. **结果必须带译文才允许生成**。合并逻辑抽成 `sentence-stream-state.ts` 的纯函数（`appendTranslation` / `settleTranslation` / `setStreamKeywords` / `toSentenceLearningResult`），`toSentenceLearningResult()` 在没有译文时返回 `null`，控制器拿到 `null` 就不写历史、不设置当前结果。不变量变成可测的，而不是散落在回调里的 if。
2. **后到的那半不许抹掉先到的**（这是同一个 bug 的另一半）：译文本地落地时不再把 `keywords` 重置成 `[]`，重点词落地时也不覆盖已经存在的译文。
3. **已经写坏的缓存条目在读入时丢弃**（`readTranslationHistoryEntries`）。历史索引是从这个函数建的，所以坏条目既不会被渲染也不会短路请求；下一次翻译会用完整结果覆盖同一句话的记录——自愈。

回归测试（`test-translation-stream-card.mjs`，7 条）：卡片先于答案存在、译文原位流式更新、重点词后到、重点词失败不影响译文、**没有译文就不产出结果**、两半无论谁后到都不互相清空、空白 delta 不会把已流式出来的文字抹掉、坏缓存条目被丢弃。

### 4.1 第二次反馈：翻完了还是空白，切到「聊天」再切回来才出现

这一条把真正的元凶抓出来了：**`setTranslationState('')`**。这个函数的名字像"设置状态文本"，实际做的是
`replaceTranslationResultText(translationResultElement, message)` —— 把**整个结果区**的 `textContent` 换成这句话。
我在译文流成功之后顺手调了一次 `setTranslationState('')` 想"清掉状态"，结果就是把刚填好的卡片清空；
数据在 `currentEnglishLearningResult` 里完好，所以切到「聊天」再切回「翻译」时按状态重渲染，内容又出现了。
两个截图正好是这个组合。

修法两层：

1. `replaceTranslationResultText()` 对**空消息**改成 no-op。空消息本来也没有语义——它不该等于"清空面板"。
   真正的消息（加载中、失败原因）照旧替换。
2. 成功路径不再调用 `setTranslationState('')`；卡片本身就是输出，那一行只用于"还没东西"和"失败了"。

顺带修了同一处的另一个漏：句子走流式路径后**没有写 `lastTranslatedText`**，于是同一段选区再次"稳定"时会重复翻译
一次（多花钱、界面闪一下、也可能留下半截卡片）。现在结果一落地就记下来，自动翻译会跳过它。

测试：`test-translation-action-layout.mjs` 加了"空消息不得触碰结果区、非空消息仍然替换"两条。

### 4.2 第三次反馈：内容有了但被截断，重点词报"没有返回有效 JSON"

现象：译文停在半个括号处（"…二进制非奇异矩阵（"），重点词那半直接失败，切换标签也不变（说明是**存下来的数据**就是残缺的）。

原因是**输出预算**。两半的 `maxOutputTokens` 我按"一句话用不了多少"设成了 512 / 768，但在**关不掉思考的模型**上，
**思考 token 和正文共用同一份 `max_tokens` 预算**——思考先吃掉大半，正文写到一半就撞上限，`finish_reason: length`。
重点词那半更惨：JSON 没写完，连 `{` 都没闭合，解析自然失败。旧路径之所以没事，是因为它给的是 4096。

改动：

1. **预算按"上限不是目标"重设**：译文 2048、重点词 3072。（caps 不影响实际生成量，只在需要时兜住。）
2. **截断要认出来，不能当成完整答案**：`done` 消息带上 `finishReason`；`length` 时译文照旧显示，但卡片上写明
   "被模型的输出上限截断（思考过程与正文共用预算）"，并**不写历史缓存**——否则下次会直接从缓存里拿回半句话。
   重点词那半同理，失败原因改成"输出被输出上限截断"，而不是含糊的"没有返回有效 JSON"。
3. 若正文一个字都没生成且 `finish_reason: length`，后台直接报"思考过程占满了输出预算"，并提示换模型或重试。

> 顺带说明用户侧的一个自检点：设置 → 高级设置里的"最大输出 Token"也会夹住这两个值（`min(任务上限, 配置值)`）。
> 如果那里被调到很小，两半都会被截断——提示文案里现在直接点名了这一点。

测试：`test-translation-prompts.mjs` 增加"预算必须给关不掉思考的模型留出空间"（≥2048，且重点词不低于译文）。

## 5. 保住的旧路径

流式端口不存在时（典型情况：页面比后台新，刷新页面只换页面 chunk、不换 service worker），会退回原来的 `pdf-helper:ai-chat` 一次性请求，并在状态栏说明"本次不会逐字显示"。词卡（不是句子）仍走原来的一次性 JSON 请求——它的输出字段本来就多，且不是"第一时间要看到译文"的场景。

## 6. 还没做的（如果要更快）

- **本地词表预筛**：内置 CET-6/词频表，客户端决定哪些词值得学，模型只负责译。可以把提示词里那 6 条筛选/排除标准整段删掉，输出再少一截。
- **跨 PDF 的句子缓存**：现在只按"当前 PDF"缓存历史结果（`translation-history.ts`），同一句在别的 PDF 里重复出现仍要重新翻译。
- **给翻译单独指定一个更快的模型**：路由里「翻译与英语学习」可以指到任意连接，把它指到最快的那个模型是最省事的一档。

## 7. 测试

- `scripts/test-translation-prompts.mjs`：提示词契约——译文那一半要纯文本（不能出现 `JSON 格式`）、重点词那一半保留 6 个上限与筛选标准但没有 `reason`、`sourceTextLatex` 只在有公式时出现、聊天助手那套规则（`[[PDF:`、`memory.upsert`、Agent 工具）不得出现、用户的学习偏好排在规则之后、两半按 `task` 分派、token 上限保持小、公式检测只对公式生效。
- `scripts/test-translation-stream-card.mjs`：真实 DOM 里卡片**先于答案存在**（两个区块 + "正在挑选重点词…"）、译文在原位逐字更新且光标在结束后消失、重点词到达后替换占位、重点词失败时译文不受影响。
- `scripts/test-built-extension.mjs`：打包版后台**注册了** `pdf-helper:ai-translate-stream-v1` 端口（看到 `started` 或 `error` 即算通过；端口不存在时会立刻断开——那正是"翻译永远不出现"的样子）。
