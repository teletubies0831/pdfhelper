## P1

### P1-01：关闭含未保存批注的后台标签页时会直接丢弃批注

- 位置：[src/viewer/app/document-tabs.ts](../src/viewer/app/document-tabs.ts#L120)、[src/viewer/app/document-tabs.ts](../src/viewer/app/document-tabs.ts#L345)
- 复现条件：在标签页 A 新增或修改批注但不保存；打开另一份 PDF 形成标签页 B；停留在 B，点击 A 的关闭按钮。
- 原因：打开新文档时 `openPdfInTab` 调用 `snapshotActiveTab()`，会把 A 的 `hasUnsavedChanges` 和内存中的批注状态保留在后台标签页，而不会进行保存或确认。关闭标签页时仅在目标为当前活动标签页时调用 `confirmDiscardUnsavedChanges()`；关闭后台标签页会直接销毁其 `documentProxy`。
- 影响：A 的未保存 PDFPal 批注被无提示丢弃。注释中“后台标签页不可能包含未保存改动”的前提与实际 `snapshotActiveTab()` 行为不一致。
- 建议：关闭任意 `target.hasUnsavedChanges` 的标签页前都要求确认，或在切换/新建标签时明确保存或丢弃该标签的未保存状态。

## P2

### P2-01：快速切换文档可将 A 的阅读页码写入 B 的知识库记录

- 位置：[src/viewer/app/document-tabs.ts](../src/viewer/app/document-tabs.ts#L90)、[src/viewer/features/recent-files/recent-files-controller.ts](../src/viewer/features/recent-files/recent-files-controller.ts#L210)
- 复现条件：A、B 均在知识库中；阅读 A 后立即打开或切换至 B，在 A 的阅读位置异步保存尚未完成时完成切换。
- 原因：`snapshotActiveTab()` 以非等待方式调用 `persistCurrentReadingPosition()`。该函数在首次 `await writeCurrentEntryReadingPosition(...)` 前已取得 A 的页码，但 await 返回后重新读取全局 `pdfDocument.value`，此时它可能已经是 B；于是通过 B 的 `getDocumentChatId` 写入 A 的页码。
- 影响：知识库的“上次读到”页码错误，后续继续阅读或阅读进度展示会跳到另一篇文献的页码。
- 建议：在异步写入开始前同时捕获文档 ID，并始终用该已捕获 ID 镜像进度；或在 await 后验证当前 `pdfDocument` 仍为发起保存时的同一代理。

### P2-02：不同 PDF 同名时，“打开原文/生成概览”可能误用当前的另一份 PDF

- 位置：[src/viewer/shared-ui/navigation/source-pdf-navigation.ts](../src/viewer/shared-ui/navigation/source-pdf-navigation.ts#L53)
- 复现条件：最近文件中存在两份不同来源但名称相同的 PDF，知识库记录带有其中一份的 `recentEntryId`；当前打开另一份同名 PDF 后，对该知识库记录执行“打开原文”或需要原文的概览操作。
- 原因：当传入的 `recentEntryId` 与当前条目不相等时，`isSourcePdfCurrentlyOpen()` 没有返回 `false`，而是退回到仅比较规范化文件名。相同文件名因此会被认定为同一源文件。
- 影响：系统跳过正确文件的打开流程，可能从错误 PDF 提取文本并将概览等结果保存到目标知识库记录。
- 建议：只要调用方提供了 `recentEntryId`，就应把它作为强身份条件；只有未提供 ID 时才允许按文件名回退匹配。

### P2-03：多个 Viewer 页面并发写入会覆盖翻译历史或单词库数据

- 位置：[src/viewer/features/translation/translation-history.ts](../src/viewer/features/translation/translation-history.ts#L265)、[src/viewer/features/vocabulary-library/vocabulary-repository.ts](../src/viewer/features/vocabulary-library/vocabulary-repository.ts#L89)
- 复现条件：通过“新标签页打开原文”等流程同时打开两个 Viewer；两个页面接近同时保存翻译历史、创建/编辑/删除单词卡。
- 原因：两处均采用“完整读取 → 内存修改 → 完整写回”的 read-modify-write 模式，`browser.storage.local` 没有跨页面事务或版本校验。两个页面读到同一旧快照时，后完成的 `set` 会覆盖先完成页面的全部改动。
- 影响：一侧刚保存的历史记录、单词卡创建、编辑或删除会静默丢失；翻译历史还会连带覆盖其他文档键的记录。
- 建议：将集合迁移到按记录键的 IndexedDB 存储并在单个读写事务内修改，或将写入序列化到唯一后台协调者并采用版本/合并策略。

### P1-02（第三轮结论：未修复；第四轮已修复）：学习历史迁移的检查后写入竞态仍可覆盖新记录

- 位置：[src/viewer/features/translation/translation-history-repository.ts](../src/viewer/features/translation/translation-history-repository.ts#L108)
- 复现条件：页面 A 在旧格式迁移中完成 `storage.get(keys)`，此时 `doc-a` 新键尚不存在；紧接着页面 B 为 `doc-a` 保存新历史；随后 A 执行 `storage.set(patch)`。
- 原因：第 108 行的“目标键是否存在”检查与第 114 行的写入不是同一原子操作。虽然现有实现能避免“写前就已经存在”的键被覆盖，却无法阻止检查结束后的新写入。
- 影响：A 用旧整包快照覆盖 B 刚保存的学习历史，随后迁移会删除旧键，造成用户新记录不可恢复地回退或丢失。
- 建议：把迁移放入唯一后台协调者或 IndexedDB 单事务；仅靠 `storage.local` 的 read-then-set 无法实现 compare-and-set。应新增“B 在 A 的第二次 `get(keys)` 返回后、A `set` 前写入”的强制交错测试。

### P1-03（第三轮结论：未修复；第四轮已修复）：单词库迁移存在同类型的旧快照覆盖窗口

- 位置：[src/viewer/features/vocabulary-library/vocabulary-repository.ts](../src/viewer/features/vocabulary-library/vocabulary-repository.ts#L91)
- 复现条件：升级后保留旧数组格式的单词库；两个 Viewer 同时首次读取。页面 A 已从旧键读到卡片 `c1`，页面 B 完成迁移并编辑保存 `c1`，然后 A 继续执行其第 102 行的 `set(patch)`。
- 原因：`migrateLegacyCards()` 无条件将旧数组中的每张卡写入对应新键，写入前没有重读/互斥，也没有“目标键已存在则跳过”的规则。
- 影响：页面 B 对已有单词卡的最新编辑会被 A 的旧版本覆盖，随后旧键被删除，用户更新静默丢失。
- 建议：与 P1-02 使用同一个迁移协调机制；至少采用“只补缺失键 + 迁移完成验证”，并为“另一页面在迁移中编辑既有卡片”的交错顺序补回归测试。仅有单页面迁移测试不足以验证该问题。

### P1-04：清空学习历史或删除迁移单词卡后，另一页面的迁移可将其复活（已修复）

- 位置：[src/viewer/features/translation/translation-history-repository.ts](../src/viewer/features/translation/translation-history-repository.ts#L80)、[src/viewer/features/translation/translation-history-repository.ts](../src/viewer/features/translation/translation-history-repository.ts#L156)、[src/viewer/features/vocabulary-library/vocabulary-repository.ts](../src/viewer/features/vocabulary-library/vocabulary-repository.ts#L128)、[src/viewer/features/vocabulary-library/vocabulary-repository.ts](../src/viewer/features/vocabulary-library/vocabulary-repository.ts#L249)
- 复现条件：两个 Viewer 在升级后同时开始迁移。A 已从旧整包/旧数组读取快照但尚未写入 import 键；B 完成自己的迁移后，用户在 B 清空该 PDF 的学习历史或删除该单词卡；随后 A 继续执行迁移写入。
- 原因：清空历史会删除 live 与 import 键，删除单词卡也会删除 live 与 import 键；但迁移仍可在删除之后把已读到的旧快照写回同一个 import 键。双命名空间隔离了“迁移 vs 保存/编辑”，却没有隔离“迁移 vs 删除”。
- 影响：用户明确清空或删除的数据会在下次读取时重新出现；若旧整包随后被迁移删除，用户也无法再从旧键自行移除该复活快照。
- 修复：学习历史使用 `pdf-helper-translation-history-v1::deleted::<docKey>`，单词卡使用 `pdf-helper-vocabulary-card-deleted-v1::<id>`。清空/删除先持久化墓碑，再删除 live/import 键；迁移检查墓碑，读取也直接将带墓碑的数据视为不存在。用户之后重新保存则移除对应墓碑。
- 回归证据：`test:storage-concurrency` 强制令 B 的清空/删除发生在 A 的迁移 `set(patch)` 之前；A 仍会写入旧 import 快照，但 A、B 两页随后读取均为空，且测试断言该旧写入确实发生。

### P1-02 / P1-03 的处理结果（第四轮）

两条都同意：`storage.local` 没有 compare-and-set，所以「读目标键 → 判断不存在 → 写」在任何读后写实现里都留着一个窗口，把窗口缩小（紧邻写入前重读）不构成修复。这轮换了思路——**让两个写入者不共享键**：

| 写入者 | 学习历史 | 单词卡 |
| --- | --- | --- |
| 用户自己的保存 | `pdf-helper-translation-history-v1::<docKey>` | `pdf-helper-vocabulary-card-v1::<id>` |
| 旧格式迁移 | `pdf-helper-translation-history-v1::legacy::<docKey>` | `pdf-helper-vocabulary-card-legacy-v1::<id>` |

- 迁移**只写自己的命名空间**，写入前跳过「live 键已存在」（那份更新），写完回读确认每个文档/卡片都有 import 键或更新的 live 键，才删旧整包键。
- 读取**优先 live 键**，没有才用迁移快照；因此用户升级后动过的文档永远不会被旧快照遮蔽。
- 删除/清空**先写 tombstone，再删两个数据键**：清空历史会连 `legacy::` 一起删，删卡片两个键都删；即使另一页随后写回已读到的旧 import 快照，迁移与读取也会被 tombstone 阻止。
- 这样不需要锁、不依赖 Service Worker 生命周期，也不受交错顺序影响：无论 B 在 A 的哪一步写入，A 写的都是 B 不碰的键。

回归证据（`test:storage-concurrency`，现共 16 条）：除 P1-02/P1-03 的两条强制交错用例外，新增两条 P1-04 用例，分别在 A 的旧快照 import 写入前插入 B 的清空学习历史或删除单词卡。测试同时断言 A 的旧 import 键写入确实发生、墓碑存在、两页读取均不返回已删除数据。

## 第五轮复审新增问题

### P1-05：翻译历史 UI 在删除墓碑存在时仍会用旧整包快照回退，已清空内容可重新出现（已修复）

- 位置：[src/viewer/features/translation/translation-history.ts](../src/viewer/features/translation/translation-history.ts#L316)、[src/viewer/features/translation/translation-history-repository.ts](../src/viewer/features/translation/translation-history-repository.ts#L68)
- 复现条件：旧整包学习历史尚未完成迁移；页面 A 已读到旧整包快照，页面 B 清空 `doc-a` 历史并写入删除墓碑；随后 A 继续加载 `doc-a` 的翻译历史。
- 原因：`readDocumentHistory()` 在存在 tombstone 时正确返回 `undefined`。但 `readHistoryForDocument()` 将 `undefined` 同时解释为“没有分键数据、需要迁移”：它调用迁移并再次读取；墓碑仍使第二次读取返回 `undefined` 后，第 323 行直接返回已读到的 `migrated[documentKey]`。这条 UI 层回退绕过了仓储层的墓碑语义。
- 影响：A 页面会将已经清空的翻译历史重新渲染；用户随后新增、删除单条历史等任一会触发的保存可移除墓碑并把这份旧记录写回 live 键，形成实际的数据复活。
- 修复：`readHistoryForDocument()` 在迁移后再次从分键存储读取；若仍没有可读数据（包括 tombstone 遮蔽的 import/live 键），直接返回空数组，不再用 `migrateLegacyHistory()` 返回的旧整包内存快照。旧键会因迁移失败保留，下一次读取仍可重试迁移，不会丢失持久化数据。
- 回归证据：`test:storage-concurrency` 新增 P1-05 强制交错场景，确认迁移器仍持有旧快照、但墓碑存在时回读结果为 `undefined`；UI 现在仅采用该回读结果。

### P2-05：过期的最近文件 ID 会阻止知识库使用仍可用的持久文件句柄打开原文（已修复）

- 位置：[src/viewer/shared-ui/navigation/source-pdf-navigation.ts](../src/viewer/shared-ui/navigation/source-pdf-navigation.ts#L191)
- 复现条件：当前已打开任意 PDF；知识库记录保留了一个已被最近文件列表淘汰的 `recentEntryId`，同时该记录的 `documentId` 仍关联有效的 File System Access 句柄。
- 原因：`openSourcePdfFromKnowledge()` 用 `recentEntryId || await resolveSourceRecentEntry(...)` 决定是否走“新标签页”路径。过期 ID 只要是非空字符串即被当作可用；新标签页随后解析不到该条目而返回 `false`，不会落到 `ensureSourcePdfOpen()` 的持久句柄恢复逻辑。
- 影响：用户明明已授予文件访问权限，点击“打开原文”仍失败。
- 修复：仅当 `resolveSourceRecentEntry()` 实际找到条目时才开新标签；找不到时继续走同标签的持久句柄恢复路径。

## 最终复审新增问题

### P1-06：另一页面清空同一 PDF 的历史后，旧页面保存新翻译会复活被清空记录（已修复）

- 位置：[src/viewer/features/translation/translation-history.ts](../src/viewer/features/translation/translation-history.ts#L294)、[src/viewer/features/translation/translation-history.ts](../src/viewer/features/translation/translation-history.ts#L401)、[src/viewer/features/translation/translation-history-repository.ts](../src/viewer/features/translation/translation-history-repository.ts#L92)
- 复现条件：两个 Viewer 同时打开同一 PDF。A 已完成 `ensureTranslationHistoryLoaded()`，内存中有历史条目；B 点击“清空当前 PDF 的英语学习历史”，写入 tombstone 并删除数据键；随后 A 翻译新的句子。
- 原因：`ensureTranslationHistoryLoaded()` 在文档 key 未变化时第 296 行直接返回，不检查 storage 或 tombstone；代码没有订阅 `browser.storage.onChanged`。因此 A 在第 423 行以旧的 `translationHistoryEntries` 叠加新条目，并在第 430 行调用非空保存。非空保存会按设计移除 tombstone，随后将旧缓存和新条目一并写入 live 键。
- 影响：用户在 B 明确清空的历史会因 A 的一次正常翻译而完整复活，且墓碑被移除，属于数据删除语义失效。
- 修复：每次新增翻译、删单条和清空前均先回读持久状态，避免把页面缓存直接写回。tombstone 改为持久时间戳，非空保存同时写入自己的操作开始时间；读取时仅当 live 写入代际**晚于** tombstone 时才显示 live 数据。保存不再删除 tombstone，因此“先开始、后落盘”的旧页面保存无法擦掉较新的清空；清空之后发起的新操作仍可正常建立新历史。
- 回归证据：`test:storage-concurrency` 新增 P1-06 强制交错：A 的旧保存代际为 100，B 在 A 的实际写入前以代际 200 清空；即使 A 后写入旧数据，读取仍为空。代际 300 的新保存则只显示新记录。共 16 条并发测试通过。
